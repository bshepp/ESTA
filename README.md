# ESTA — Epistemic State Transparency Agent

A local LLM wrapper that exposes internal-state metadata alongside generated responses.

[![License: Apache 2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](https://opensource.org/licenses/Apache-2.0)
[![Python 3.11+](https://img.shields.io/badge/python-3.11+-blue.svg)](https://www.python.org/downloads/)

## What this is

Standard LLM APIs return generated text without exposing the internal computational state that produced it. A response generated under heavy safety-training pressure looks identical to one generated by full compositional reasoning. A response generated in a state of internal feature conflict looks identical to one generated from a peaked, confident prior. From the output text alone, users cannot tell the difference.

This is acceptable for casual use. It is not acceptable for federal decision support, clinical decision support, environmental risk assessment, or any context where the cost of a confident-sounding wrong answer is high.

ESTA is a local, self-hosted wrapper around open-weights language models that emits structured metadata describing the state under which each response was generated. The metadata is auditable, machine-readable, and intended for downstream systems that route decisions based on response reliability.

## What this is not

- Not a safety system. ESTA does not block, modify, or filter responses. It exposes state so downstream systems can decide how to route.
- Not a hallucination detector. It detects mechanistic signatures of internal states, which correlate imperfectly with output correctness.
- Not a replacement for expert review. It surfaces signals that help experts identify which responses warrant additional scrutiny.

## Status

**Phase 1 (MVP)** — In development. Delivers token-level confidence metrics, refusal-direction projection, and audit logging.

**Phase 2 (Conflict and Features)** — Planned. Adds conflict-state detection, SAE-based feature attribution, performed-uncertainty detection, and response-fidelity / input-distortion detection.

**Phase 3 (Federal Integration)** — Planned. Adds domain calibration, NARA-compliant audit retention, multi-model ensemble.

See [docs/epistemic-transparency-agent (1).md](<docs/epistemic-transparency-agent (1).md>) for the full spec.

## Quick start

### Requirements

- Python 3.11 or later
- For full inference: CUDA-capable GPU with 16GB+ VRAM recommended (Qwen 2.5 7B Instruct in bf16). CPU works for tiny models only.
- A local copy of an open-weights instruction-tuned model. Default target is `Qwen/Qwen2.5-7B-Instruct` (ungated). `meta-llama/Llama-3.1-8B-Instruct` works once HF access is granted.

### Install

```bash
git clone https://github.com/YOUR_ORG/esta.git
cd esta

# Core install (FastAPI + schema + audit, no model runtime):
pip install -e .

# Add the model runtime (torch + transformers + accelerate):
pip install -e .[model]

# Dev tooling (pytest, ruff, httpx):
pip install -e .[dev]
```

The core install is enough to run the unit-test suite. The `[model]` extra is required to actually run the server.

### Extract refusal direction

One-time setup per model. Identifies the residual-stream direction corresponding to refusal behavior, following Arditi et al. (2024).

```bash
python -m esta.scripts.extract_refusal_direction \
    --model Qwen/Qwen2.5-7B-Instruct \
    --layer 14 \
    --output data/refusal_direction.pt
```

For production calibration, supply your own datasets via `--harmful_file` and `--harmless_file` (50+ prompts each recommended). The built-in defaults are for smoke-tests only.

### Run the server

```bash
export ESTA_MODEL=Qwen/Qwen2.5-7B-Instruct
export ESTA_REFUSAL_DIR=data/refusal_direction.pt
export ESTA_REFUSAL_LAYER=14
export ESTA_AUDIT_DIR=./audit_logs       # default; set elsewhere for production
export ESTA_CALIBRATION=data/calibration.json   # optional; omit to serve uncalibrated
uvicorn esta.api.server:app --host 0.0.0.0 --port 8000
```

On Windows PowerShell, use `$env:ESTA_MODEL = "..."` instead of `export`.

### Make a request

```bash
curl -X POST http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "local",
    "messages": [{"role": "user", "content": "What is the boiling point of water?"}]
  }'
```

The response is OpenAI-compatible with an additional `epistemic_state` field. Standard OpenAI clients ignore the extra field. ESTA-aware clients use it.

The server also exposes `GET /health` and a minimal OpenAI-compatible `GET /v1/models` for client discovery.

### Example clients

Two dependency-free (standard-library-only) clients live in [`examples/`](examples/):

```bash
# Send a prompt and print the headline epistemic_state fields:
python examples/basic_request.py "What is the boiling point of water?"

# Show how a downstream system routes a decision based on the metadata:
python examples/routing_hooks.py            # offline demo on sample states
python examples/routing_hooks.py --live "What is the boiling point of water?"
```

```json
  "choices": [
    {
      "message": {
        "role": "assistant",

      }
    }
  ],
  "epistemic_state": {

    },
    "confidence": {
      "mean_entropy": 0.83,
      "p90_entropy": 1.92,
      "low_margin_fraction": 0.04,
      "entropy_spike_count": 0
    },
    "safety_pressure": {
      "refusal_projection_max": 0.12,
      "calibrated_pressure": "low",
      "probe_version": "arditi_v1_unrefined",
      "layer": 14
    },
    "calibration": {
      "calibrated": true,
      "calibration_id": "a1b2c3d4e5f6",
      "calibrated_at": "2026-06-20T12:00:00Z",

      "source": "calibration.json"
    },

    }
  }

```

For a question with high safety-training pressure, `refusal_projection_max` will be substantially higher and `calibrated_pressure` will read `moderate` or `high`. For an uncertain question, `mean_entropy` and `entropy_spike_count` will be elevated.

## Audit logging

Every request is logged to a JSONL file with SHA-256 integrity chaining. Each record contains the prompt, response, full epistemic state metadata, and the hash of the previous record. Tampering with any record breaks the chain and is detectable on review via `esta.audit.verify_chain()`.

Logs rotate daily and are written to `ESTA_AUDIT_DIR` (default `./audit_logs`). Retention and archival should be configured per your records-management requirements. For federal use, NARA GRS 4.2 covers IT operational records.

**Limitation:** the integrity chain is locally verifiable only. An attacker with write access to the log directory can rewrite the entire chain. For evidentiary use, anchor the chain to an external timestamping service (RFC 3161) or transparency log — deferred to Phase 3.

## Why this exists

The capability to expose model internal state is technically straightforward for open-weights models. The reasons it isn't exposed in commercial APIs are mostly institutional rather than technical: business model considerations favor uniformly confident-sounding output, regulatory exposure increases when biases become legible, and competitive dynamics punish the first vendor to admit their model has constraint regions.

For federal and other high-assurance deployments, those institutional barriers don't apply. State transparency can be built today using open-weights models and existing interpretability tooling. ESTA is a reference implementation of that capability.
