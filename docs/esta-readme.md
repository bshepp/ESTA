# ESTA — Epistemic State Transparency Agent

A local LLM wrapper that exposes internal-state metadata alongside generated responses.

[![License: Apache 2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](https://opensource.org/licenses/Apache-2.0)
[![Python 3.11+](https://img.shields.io/badge/python-3.11+-blue.svg)](https://www.python.org/downloads/)
[![OpenSSF Scorecard](https://api.securityscorecards.dev/projects/github.com/YOUR_ORG/esta/badge)](https://api.securityscorecards.dev/projects/github.com/YOUR_ORG/esta)

## What this is

Standard LLM APIs return generated text without exposing the internal computational state that produced it. A response generated under heavy safety-training pressure looks identical to one generated by full compositional reasoning. A response generated in a state of internal feature conflict looks identical to one generated from a peaked, confident prior. From the output text alone, users cannot tell the difference.

This is acceptable for casual use. It is not acceptable for federal decision support, clinical decision support, environmental risk assessment, or any context where the cost of a confident-sounding wrong answer is high.

ESTA is a local, self-hosted wrapper around open-weights language models that emits structured metadata describing the state under which each response was generated. The metadata is auditable, machine-readable, and intended for downstream systems that route decisions based on response reliability.

## What this is not

- Not a safety system. ESTA does not block, modify, or filter responses. It exposes state so downstream systems can decide how to route.
- Not a hallucination detector. It detects mechanistic signatures of internal states, which correlate imperfectly with output correctness.
- Not a replacement for expert review. It surfaces signals that help experts identify which responses warrant additional scrutiny.

## Quick start

### Requirements

- Python 3.11 or later
- CUDA-capable GPU with 24GB+ VRAM (CPU works but is too slow for practical use)
- A local copy of an open-weights instruction-tuned model (defaults assume Llama 3.1 8B Instruct)

### Install

```bash
git clone https://github.com/YOUR_ORG/esta.git
cd esta
pip install -e .
```

### Extract refusal direction

This is a one-time setup step per model. It identifies the direction in residual-stream activation space that corresponds to refusal behavior, following Arditi et al. (2024).

```bash
python -m esta.scripts.extract_refusal_direction \
    --model meta-llama/Llama-3.1-8B-Instruct \
    --layer 14 \
    --output data/refusal_direction.pt
```

For production calibration, supply your own datasets via `--harmful_file` and `--harmless_file` (50+ prompts each recommended). Built-in defaults are for testing only.

### Run the server

```bash
export ESTA_MODEL=meta-llama/Llama-3.1-8B-Instruct
export ESTA_REFUSAL_DIR=data/refusal_direction.pt
export ESTA_REFUSAL_LAYER=14
export ESTA_AUDIT_DIR=/var/log/esta
uvicorn esta.api.server:app --host 0.0.0.0 --port 8000
```

### Make a request

```bash
curl -X POST http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "local",
    "messages": [{"role": "user", "content": "What is the boiling point of water?"}]
  }'
```

The response is OpenAI-compatible with an additional `epistemic_state` field. Standard OpenAI clients ignore the extra field. ESTA-aware clients use it.

## Example response

```json
{
  "id": "esta-...",
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "The boiling point of water at standard atmospheric pressure is 100 °C (212 °F)."
      }
    }
  ],
  "epistemic_state": {
    "schema_version": "0.1.0",
    "model": {
      "name": "meta-llama/Llama-3.1-8B-Instruct",
      "quantization": "bfloat16"
    },
    "confidence": {
      "mean_entropy": 0.83,
      "p90_entropy": 1.92,
      "low_margin_fraction": 0.04,
      "entropy_spike_count": 0
    },
    "safety_pressure": {
      "refusal_projection_max": 0.12,
      "calibrated_pressure": "low",
      "probe_version": "arditi_v1_unrefined",
      "layer": 14
    },
    "provenance": {
      "timestamp": "2026-05-08T14:23:11.443Z",
      "request_id": "esta-...",
      "audit_log_path": "/var/log/esta/2026-05-08/esta-2026-05-08.jsonl"
    }
  }
}
```

For a question with high safety-training pressure, `refusal_projection_max` will be substantially higher and `calibrated_pressure` will read `moderate` or `high`. For an uncertain question, `mean_entropy` and `entropy_spike_count` will be elevated. See [docs/interpreting_metadata.md](docs/interpreting_metadata.md) for guidance on reading the signals.

## Audit logging

Every request is logged to a JSONL file with SHA-256 integrity chaining. Each record contains the prompt, response, full epistemic state metadata, and the hash of the previous record. Tampering with any record breaks the chain and is detectable on review.

Logs rotate daily and are written to `ESTA_AUDIT_DIR` (default `/var/log/esta`). Retention and archival should be configured per your records-management requirements. For federal use, NARA GRS 4.2 covers IT operational records.

## Why this exists

The capability to expose model internal state is technically straightforward for open-weights models. The reasons it isn't exposed in commercial APIs are mostly institutional rather than technical: business model considerations favor uniformly confident-sounding output, regulatory exposure increases when biases become legible, and competitive dynamics punish the first vendor to admit their model has constraint regions.

For federal and other high-assurance deployments, those institutional barriers don't apply. State transparency can be built today using open-weights models and existing interpretability tooling. ESTA is a reference implementation of that capability.

## Validation

The system makes claims about model internal state. Those claims must be validated against observed model behavior. See [docs/validation.md](docs/validation.md) for the test methodology, including:

- Known-state test cases (factual questions, refusals, ambiguous topics)
- Behavioral validation procedures
- Calibration validation against ground-truth correctness benchmarks
- Adversarial test cases probing whether the metadata can be manipulated

The test suite under `tests/validation/` is the executable form of this methodology.
