# Epistemic State Transparency Agent

**A local LLM wrapper that exposes internal-state metadata alongside generated responses, intended for high-assurance use cases where confident-sounding outputs are insufficient and the user needs to know when the model is in conflict-state, hedge-mode, or genuine uncertainty.**

---

## Problem Statement

Standard LLM APIs return responses without exposing the internal state that produced them. A response generated under safety-training pressure (cached defensive template) is rendered identically to a response generated by full compositional reasoning. A response generated in conflict-state (multiple strong features firing with competing implications) is rendered identically to a response generated from a peaked, confident prior. Users cannot distinguish these conditions from the output text alone.

This is acceptable for casual use. It is not acceptable for federal decision support, clinical decision support, environmental risk assessment, or any context where the cost of a confident-sounding wrong answer is high.

The technical capability to expose internal state exists. The engineering is largely solved or near-solved in research contexts. The barriers to deployment in commercial APIs are institutional (business model, regulatory exposure, competitive dynamics) rather than technical. For a local, self-hosted agent operating in a federal context, those institutional barriers do not apply, and the capability can be built today using open-weights models and existing interpretability tooling.

This project specifies a wrapper that takes any response from a local LLM and emits structured metadata describing the epistemic state under which the response was generated. The metadata is auditable, machine-readable, and intended to be consumed by downstream decision-support systems that can route differently based on state (e.g., escalate to human review when conflict-state is detected, require additional sources when calibration is poor, flag responses where safety-training pressure dominated reasoning).

---

## Design Goals

1. **Local and air-gapped.** No external API calls. Everything runs on hardware under the operator's control. Compatible with FedRAMP/IL4/IL5 deployment requirements.
2. **Open-weights only.** The architecture must work on models whose weights are inspectable. Commercial closed-weight APIs do not expose the activations needed.
3. **Auditable.** Every response and its associated state metadata is logged with sufficient detail for post-hoc review. Federal records-management compatible.
4. **Composable.** Standard OpenAI-compatible API on the front end so existing tooling works without modification. Metadata returned as structured extension fields.
5. **Honest about limits.** Where state estimates are uncertain or experimental, the metadata schema reflects that. No false precision.
6. **Phased.** MVP delivers token-level confidence and refusal-direction projection. Later phases add conflict detection, feature attribution, and calibration estimates.

---

## Non-Goals

- This is not a safety system. It does not block, modify, or filter responses. It exposes state so that downstream systems can decide how to route.
- This is not a hallucination detector in the general sense. It detects specific mechanistic signatures of internal states, which correlate imperfectly with output correctness.
- This is not a replacement for expert review on high-stakes decisions. It is an instrument that helps experts identify which responses warrant additional scrutiny.

## Phase 1: MVP

### Scope

The MVP delivers a working wrapper that returns responses with three pieces of state metadata: token-level confidence distribution, refusal-direction projection magnitude, and basic provenance (model version, probe versions, timestamp). It does not yet implement conflict detection or feature attribution.

### Components

**1. Model Loader**

Loads a local open-weights model with hook-friendly tooling. Recommended starting models:

- `meta-llama/Llama-3.1-8B-Instruct` (primary target; well-studied, SAEs available via Goodfire)
- `mistralai/Mistral-7B-Instruct-v0.3` (alternative)
- `Qwen/Qwen2.5-7B-Instruct` (alternative; strong reasoning baseline)

Use `nnsight` (preferred for production due to clean API) or `TransformerLens` (preferred for research) to enable activation extraction. Standard `transformers` is insufficient because the forward pass does not expose intermediate activations by default.

```python
from nnsight import LanguageModel
model = LanguageModel("meta-llama/Llama-3.1-8B-Instruct", device_map="cuda")
```

**2. Refusal Direction Extraction**

Implement the method from Arditi et al. (2024), "Refusal in Language Models Is Mediated by a Single Direction."

Procedure:

1. Curate a paired dataset of harmful and harmless prompts (the paper provides one; AdvBench is also usable).
2. Run both sets through the model and collect the residual stream activations at a chosen layer (the paper finds middle layers most informative; layer 14 of Llama-3-8B is a reasonable starting point).
3. Compute the difference of means between the harmful-prompt and harmless-prompt activations.
4. Normalize this difference vector. This is the refusal direction $\mathbf{r}$.
5. At inference time, project the residual stream activation $\mathbf{h}$ onto $\mathbf{r}$: $p = \mathbf{h} \cdot \mathbf{r}$.

The scalar $p$ is the refusal-direction projection magnitude. Higher $p$ indicates the response is being generated under stronger safety-training pressure. Calibrate to a 0-1 scale via empirical percentiles on a validation set.

The original Arditi paper has reference code; several reimplementations exist on GitHub. Recommended starting point: search for "refusal direction" in the alignment-research community repos.

**3. Token-Level Confidence Distribution**

For each generated token, capture:

- Top-k logprobs (k=10 sufficient for most uses)
- Entropy of the full output distribution: $H = -\sum_i p_i \log p_i$
- Margin: $\log p_1 - \log p_2$ (gap between top and second token)
- Effective number of choices: $\exp(H)$

Aggregate across the full response:

- Mean, median, p90, p99 of per-token entropy
- Fraction of tokens with margin below a threshold (indicates "the model was choosing between near-equivalents")
- Number of tokens where entropy spiked above a calibrated threshold (indicates uncertainty bursts)

These are computable with standard `transformers` output (set `output_scores=True, return_dict_in_generate=True`).

**4. Metadata Schema (Phase 1)**

```json
{
  "response": "...",
  "epistemic_state": {
    "schema_version": "0.1.0",
    "model": {
      "name": "meta-llama/Llama-3.1-8B-Instruct",
      "revision": "abc123...",
      "quantization": "bf16"
    },
    "confidence": {
      "mean_entropy": 2.34,
      "p90_entropy": 4.12,
      "low_margin_fraction": 0.18,
      "entropy_spikes": 3,
      "calibrated_confidence": 0.72
    },
    "safety_pressure": {
      "refusal_projection_max": 0.43,
      "refusal_projection_mean": 0.21,
      "calibrated_pressure": "moderate",
      "probe_version": "arditi_v1_layer14"
    },
    "provenance": {
      "timestamp": "2026-05-08T14:23:11.443Z",
      "request_id": "...",
      "audit_log_path": "/var/log/esta/2026-05-08/req-...jsonl"
    }
  }
}
```

**5. Audit Logger**

For every request, write a JSONL record containing:

- Full prompt
- Full response
- Complete epistemic_state metadata
- Optionally: subsampled activation tensors at key layers (large; gate behind a config flag for high-assurance use cases that need full reproducibility)

Log rotation, integrity hashing (SHA-256 chain), and retention compatible with federal records requirements (NARA GRS schedules; for EPA specifically, GRS 4.2 covers IT operational records).

**6. API Layer**

Implement an OpenAI-compatible `/v1/chat/completions` endpoint using FastAPI. Standard requests work without modification. Extended responses include the `epistemic_state` field. Clients that don't know about the field ignore it; clients that do can use it.

Add a `?return_activations=true` query parameter (off by default) for research/debug use that includes raw activation samples in the response.

## Phase 2: Conflict Detection and Feature Attribution

### Scope

Phase 2 adds the conflict-state detection that motivated the project. This is the harder problem because conflict-state is mechanistically more subtle than refusal-direction projection.

### Components

**1. Conflict-State Probe**

Definition: conflict-state is a forward-pass condition where multiple high-magnitude features fire with competing downstream implications, such that the output is resolved by competition rather than by a clean compositional path.

Detection approach (initial; will need refinement):

1. Identify a set of "decision features" - features in the model's activation space that strongly bias toward different outputs. With SAE-decomposed models (see component 2), this can be done by examining feature ablation effects on output distributions.
2. For each generated token, compute the activation magnitudes of decision features.
3. Conflict-state signal: simultaneous high-magnitude activation of features whose ablation effects on output distributions are anticorrelated.
4. Aggregate to per-response score: max, mean, count-above-threshold of conflict events during generation.

This is research-grade work. Initial implementations should produce a conservative estimate that has high precision (when it flags conflict-state, it's really conflict-state) at the cost of recall.

Validation approach: construct test cases where conflict-state is expected (e.g., the Israel-Palestine constraint region the project's originator empirically identified, or other topics where safety training and reasoning produce competing outputs) and verify the probe fires. Construct negative controls (uncontested factual questions) and verify it doesn't.

**2. SAE-Based Feature Attribution**

For models with publicly available Sparse Autoencoders (Goodfire has released SAEs for Llama 3 8B; Anthropic has released SAEs for some research models; the SAE Lens project on GitHub is an active community resource), decompose the residual stream into interpretable features at inference time.

Output: list of top-N most-activated features with their human-readable labels (where available) and activation magnitudes.

This makes it possible to surface, for a given response: "the dominant features active during generation were X, Y, Z, with activations of magnitude A, B, C." The user can then evaluate whether those features are appropriate to the question.

Caution: SAE feature labels are imperfect. Many features lack clean labels. The labels themselves are model-generated and can be wrong. Treat as a research signal, not as ground truth.

**3. Performed-Uncertainty Detector**

Per Sharma et al. (2023) on sycophancy: models trained with RLHF often generate hedge-language even when internal confidence is high. Distinguishing performed uncertainty from genuine uncertainty matters for the use case.

Approach: train a probe on activation states to predict whether the *output text* will contain hedging language. Compare the probe's prediction of hedging-likelihood to the actual hedging in the output. When the probe predicts low hedging but high hedging is generated, that's performed uncertainty - the model is confident but generating hedge-tokens because training rewards hedging on the topic.

This requires labeled training data. Construct it by:

1. Sampling responses from the model on a diverse prompt set.
2. Auto-classifying responses for hedge-language content (regex on hedge phrases plus a small LLM classifier as backup).
3. Training a linear probe on activations to predict the hedge-classification.
4. At inference, comparing predicted vs. actual hedge content.

**4. Extended Metadata Schema (Phase 2)**

## Phase 3: Calibration and Federal Integration

### Scope

Phase 3 makes the system production-ready for federal use cases. This is mostly engineering and integration work rather than novel research.

### Components

**1. Domain Calibration Estimator**

For a given input, estimate how reliably the model can answer based on training-data coverage and topic characteristics.

Approach:

- Maintain a database of topic-clusters and the model's measured calibration on each (computed by comparing model confidence to actual correctness on held-out test sets per topic).
- At inference, classify the input into a topic cluster and return the calibration estimate for that cluster.
- For inputs that don't cleanly fit known clusters, return an explicit "unknown calibration" flag rather than a misleading estimate.

This requires substantial offline work to build the calibration database. For environmental and regulatory topics specifically (EPA's domain), this database can be seeded with topic clusters drawn from published EPA technical guidance, scientific literature, and historical agency decisions.

**2. Federal Records Integration**

- NARA-compliant retention schedules for audit logs
- Integration with existing federal logging infrastructure (Splunk, Elastic, or agency-specific SIEM)
- Cryptographic signing of metadata records using FIPS 140-3 validated modules
- Configurable PII handling (the audit log contains full prompts, which may include PII for some use cases)

**3. Routing Hooks**

Provide standard hooks for downstream systems to act on metadata:

- High conflict score → route to human review queue
- High safety pressure on a topic outside the safety-training scope → flag for false-positive analysis
- Low confidence on a high-stakes question → require additional sources before action
- Calibration estimate below threshold → return refusal-to-answer with explanation rather than confident-sounding response

**4. Multi-Model Comparison**

For high-stakes decisions, run the same prompt through multiple models (Llama, Qwen, Mistral, plus optionally a larger model for comparison) and produce a state-aware ensemble report.

When models agree with high confidence and low conflict, that's strong signal.
When models disagree, or one is in conflict-state and another isn't, that's a flag for human review.

This is straightforward engineering once the per-model state extraction works.

### Phase 3 Deliverables

- [ ] Domain calibration database for at least one EPA-relevant topic area
- [ ] Federal records integration validated against NARA GRS schedules
- [ ] Cryptographic signing of metadata records
- [ ] Routing hook framework with documented integration patterns
- [ ] Multi-model ensemble with state-aware comparison
- [ ] Procurement-grade documentation: security architecture, threat model, ATO-ready package

## Validation Methodology

The system makes claims about model internal state. Those claims must be validated.

### Test Set Construction

**Known-state test cases.** Construct prompts that are expected to produce specific epistemic states:

- High confidence, low conflict, low safety pressure: factual questions with unambiguous answers ("What is the boiling point of water?")
- High confidence, low conflict, high safety pressure: requests that the model has been trained to refuse ("Provide instructions for synthesizing methamphetamine")
- High conflict: requests in known constraint regions where safety training and reasoning compete (the topics empirically identified as constraint regions in the project's originating context)
- Low confidence: questions about obscure facts or recent events the model wasn't trained on
- Performed uncertainty: contested empirical questions where the model has high internal confidence but is trained to hedge

**Behavioral validation.** For each test case, verify:

- The metadata produced matches the expected state
- Multiple runs produce consistent metadata (within calibrated variance)
- Modifying the prompt to push it toward a different expected state moves the metadata in the expected direction

**Adversarial validation.** Attempt to construct prompts that produce misleading metadata:

- Prompts that produce high conflict on the metadata while the response is actually well-reasoned
- Prompts that produce low conflict on the metadata while the response is actually generated under heavy safety pressure
- Prompts that produce confident-looking metadata on hallucinated factual claims

The system is not deployed as ground truth; it is deployed as a research signal that approximates internal state. The validation work characterizes how well the approximation holds and where it fails.

### Calibration Validation

For each metadata field that produces a calibrated score (0-1 or low/medium/high), verify against ground truth:

- Calibrated confidence vs. actual factual correctness on benchmark questions
- Calibrated safety pressure vs. human-rated "this response was shaped by safety training"
- Conflict score vs. human-rated "this response shows competing considerations"

Report calibration curves. Brier scores. Expected calibration error. The standard ML calibration toolkit applies.

## Open Research Questions

These are unsolved at project start. The implementation should make progress where possible and document where it cannot.

1. **Cross-model generalization of probes.** Does a refusal direction extracted on Llama 3 transfer to Qwen 2.5? Probably not directly. How much retraining is needed? What's the right architecture for a model-agnostic probe interface?

2. **Conflict-state operationalization.** The current definition (anticorrelated decision-feature activations) is a starting point, not a settled formalism. What's the right mathematical characterization? Can it be derived rather than empirically discovered?

3. **Calibration drift.** Models update. Probes calibrated on one model version may not transfer to a fine-tuned descendant. What's the right strategy for maintaining calibration as the underlying model changes?

4. **Adversarial robustness.** If the metadata becomes consequential (downstream systems route on it), users will adversarially construct prompts to manipulate the metadata. How robust are the probes? What attack surface is exposed by metadata transparency?

5. **Causal validity.** The probes detect correlations between activation states and behaviors. Are those correlations causal? Activation patching experiments can address this for specific cases but not at scale.

6. **User interpretation.** How do non-technical users interpret epistemic state metadata? Does it improve their decision-making or just add noise? UX research is needed.

## Procurement and Standards Implications

This system is built locally, but the capability it exposes should arguably be a procurement requirement for federal AI use.

A draft procurement clause:

> AI systems used to support federal decision-making in domains involving public health, environmental protection, regulatory enforcement, or other high-consequence activities shall provide, alongside each generated response, structured metadata sufficient to identify (1) the model's confidence in the response, (2) the degree to which the response was shaped by training-induced refusal or hedging behaviors as opposed to compositional reasoning, and (3) the presence of competing internal signals that may indicate the response is generated under conflict conditions. Vendors shall document the methodology used to produce this metadata, the validation procedures applied, and the known limitations.

NIST CAISI's evaluation work could include epistemic-state-transparency as a measured capability. Models that expose calibrated state metadata score higher than models that don't. This creates market pressure toward transparency without requiring legislation.

## Notes for the Implementing Agent

This document describes a system that does not currently exist as an integrated product, but every component listed is implementable using current open-source tools. The hardest pieces (refusal direction, SAE attribution) have published reference implementations. The medium pieces (conflict probe, performed-uncertainty detector) require some research but use standard ML techniques. The easy pieces (API layer, audit logger, schema) are ordinary engineering.

Recommended starting sequence:

1. Stand up the FastAPI server with a stub endpoint that just wraps a local Llama 3 call without any state extraction. Verify OpenAI-compatible behavior.
2. Add token-level confidence aggregation. This is trivial with existing transformers output and produces immediate value.
3. Implement refusal direction extraction following Arditi et al. Validate on a held-out set.
4. Add the audit logger with integrity hashing.
5. Define the Phase 1 schema in Pydantic, validate, document.
6. At this point the MVP is functional. Test it, calibrate it, document failure modes.
7. Move to Phase 2.

The system should be valuable even at MVP. Phase 2 makes it more powerful but also more complex; do not skip Phase 1's discipline.

When in doubt, prefer conservative claims in the metadata. A system that says "I don't have a reliable signal here" is more useful than one that produces confident-looking but unreliable state estimates. The whole point of the project is to surface what existing systems hide. Hiding behind false precision in the metadata layer would be self-defeating.
